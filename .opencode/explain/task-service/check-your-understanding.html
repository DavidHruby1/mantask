Kapitola 6

Ověření porozumění

Osm otázek na strukturu, tok řízení a hranice odpovědnosti.

1. Proč get_all_tasks volá _resolve_task_filters před find_tasks?

  1. Repository přijímá pouze filtr s povinným a autorizovaným team_id.
  2. Repository neumí řadit Task bez aktivní session.
  3. Pydantic neumí parsovat seznam statusů z query.
Zobrazit odpověď

a. Resolver doplní tým a ověří přístup; repository pak řeší jen SQL filtraci.

2. Kdo vlastní úspěšný commit po create_task?

  1. insert_task, hned po db.add.
  2. FastAPI endpoint post_task.
  3. SQLAlchemy model Task při konstrukci.
Zobrazit odpověď

b. Service a repository jen připraví objekt v session; endpoint commitne, refreshne a při chybě rollbackne.

3. Co zajišťuje payload.model_dump(exclude_unset=True) při PATCH?

  1. Do mutace vstoupí jen pole, která klient skutečně poslal.
  2. Všechna pole s hodnotou None se automaticky odstraní.
  3. Task se převede přímo na SQL UPDATE statement.
Zobrazit odpověď

a. Vynechané pole zachová starý stav; explicitně poslané null zůstává přítomnou aktualizací.

4. Proč create hledá creatora přes get_team_member(team_id, user_id), ne přes get_team_member_by_id?

  1. Creator se ukládá jako User, nikoli TeamMember.
  2. Vstup zná identitu uživatele a potřebuje ji převést na týmové membership ID.
  3. get_team_member_by_id funguje pouze pro reviewera.
Zobrazit odpověď

b. creator_member_id je cizí klíč na TeamMember, zatímco autentizovaná session poskytuje user_id.

5. Která operace sdílí přístupovou bránu get_accessible_task?

  1. Jen GET detailu.
  2. GET seznamu a POST.
  3. GET detailu, PATCH a DELETE.
Zobrazit odpověď

c. Všechny tři nejprve potřebují existující Task dostupný aktuálnímu členovi aktivního týmu.

6. Kde se rozhoduje, že nový IN_PROGRESS Task dostane started_working_at?

  1. V TaskService, před voláním insert_task.
  2. V databázovém server defaultu modelu Task.
  3. V response modelu TaskRead.
Zobrazit odpověď

a. Service nastaví aktuální UTC čas jen pro tento status a předá jej repository.

7. Proč service při update kombinuje updates se stávajícími poli Task?

  1. Aby mohla validovat výsledný review invariant i při částečném payloadu.
  2. Aby obešla Pydantic validaci všech přijatých polí.
  3. Aby při každém PATCH přepsala všechna pole.
Zobrazit odpověď

a. Platnost závisí na výsledné kombinaci should_review, reviewera a data, ne jen na nově poslaných hodnotách.

8. Co znamená návrat None z get_in_progress_limit?

  1. Pro tým neplatí žádný limit.
  2. Konfigurace aplikace chybí a service vyvolá interní serverovou chybu.
  3. Limit se automaticky nastaví na databázový default bez vložení řádku.
Zobrazit odpověď

b. Default 2 platí při vytvoření řádku AppConfig; neexistující singleton je chyba konfigurace.
