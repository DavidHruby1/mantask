Kapitola 5

Napojení a rozhodnutí

Kdo službu volá, kdo vlastní stav a transakci a které záměry lze z kódu opravdu doložit.

Volající a hranice API

Jediným consumerem singletonu task_service je backend/app/api/endpoints/tasks.py. GET seznamu volá get_all_tasks. GET detailu, PATCH a DELETE nejprve volají get_accessible_task. POST volá create_task; PATCH poté update_task. Endpoint převádí SQLAlchemy objekty na TaskRead.

Stav, side effects a transakce

find_tasks, lookupy a county provádějí databázové čtení. insert_task volá db.add(task); repository update_task mění atributy spravovaného objektu. Ani jedna service metoda nevolá commit.

backend/app/api/endpoints/tasks.py:51-61 
    active_team_id = get_last_active_team_id(db, user)
    created_task = task_service.create_task(db, active_team_id, user_id, payload)

    try: 
        db.commit()
        db.refresh(created_task)
    except IntegrityError:
        db.rollback()
        raise ApiConflictError("Bootstrap data conflicts with existing records")

    return TaskRead.model_validate(created_task)

Tento výřez dokládá vlastnictví transakce endpointem: service připraví změnu, endpoint ji potvrdí a obnoví serverové hodnoty. Při integrity chybě endpoint provede rollback. Stejný vzor používá PATCH; DELETE volá db.delete přímo v endpointu.

Závislosti a vynucení pravidel

Pydantic schémata vlastní syntaktickou validaci a pravidla zjistitelná jen z payloadu, například povolený počáteční status a ne-prázdný title. Service vlastní kontroly vyžadující databázi nebo současný Task. SQLAlchemy model přidává poslední obranu v PostgreSQL: CHECK constraints a unikátní pozici.

WIP limit pochází ze singletonu AppConfig; databázový default je 2. Chybějící řádek není považován za „bez limitu“, ale za ApiInternalServerError. Jde tedy o povinnou bootstrap konfiguraci.

Cílené testy

backend/tests/schemas/test_task.py ověřuje normalizaci title/layer, datumy, počáteční statusy, review kombinace a PATCH rozlišení vynechaného title. Soubor backend/tests/services/test_tasks.py je prázdný a task API integrační testy nebyly nalezeny.

Důsledek: větvení podle členství, aktivního týmu, WIP limitu, výsledného review stavu a transakční chování endpointu nemá v repozitáři přímé automatizované pokrytí.

Trade-offs

Service bez commitu udržuje transakční rozhodnutí u HTTP use case a dovoluje endpointu mapovat databázové výjimky. Cenou je nutnost, aby každý write caller nezapomněl commitnout nebo rollbacknout.

Více validačních vrstev není čistá duplicita: schéma zná payload, service zná související řádky a model chrání databázový stav. Review invariant se ale částečně opakuje ve schématu, service a CHECK constraintu, takže změna pravidla musí zůstat synchronizovaná.

Count-before-insert je jednoduchý a čitelný, ale WIP limit není samostatný databázový constraint. Současné inserty navíc závodí o stejnou vypočtenou pozici; unikátní constraint může konflikt zachytit až při commitu.

Různá granularita chyb: list sjednocuje neexistující, neaktivní a cizí tým do TaskAccessDeniedError, zatímco detail vrací odlišné chyby pro Task, členství a Team. To může omezovat únik informací u listu, ale rozdíl není dokumentován.

Skutečně neznámý záměr

Z dostupného kódu ani dokumentace nelze určit, proč kontrola WIP limitu při create proběhne před ověřením členství creatora, proč list a detail zveřejňují odlišně podrobné chyby ani zda se počítá s retry po pozičním konfliktu. Historii nebylo nutné použít k popisu chování; tyto produktové a bezpečnostní motivace zůstávají nedoložené.
